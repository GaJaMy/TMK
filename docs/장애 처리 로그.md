# 장애 처리 로그

## 2026-05-09 문서 업로드 후 문제 생성에서 문서 조회 실패

### 증상

- 문서 업로드 API 호출 후 비동기 문제 생성 단계에서 `BusinessException: 문서를 찾을 수 없습니다.`가 발생했다.
- 실패 위치는 `AsyncDocumentQuestionGenerationService.processDocument()`의 `documentPort.findById(documentId)` 조회 지점이었다.

### 원인

- 기존 흐름은 `DocumentUseCase.uploadDocument()` 트랜잭션 안에서 문서를 저장한 직후 `@Async` 문제 생성을 바로 호출했다.
- `@Transactional`은 메서드가 끝날 때 커밋되므로, 비동기 스레드가 실행되는 시점에는 문서 저장 트랜잭션이 아직 커밋되지 않을 수 있었다.
- 비동기 스레드는 별도 스레드와 별도 DB 커넥션에서 조회하므로, 커밋 전 문서 row를 볼 수 없어 `DOCUMENT_NOT_FOUND`가 발생했다.

### 기존 시나리오

```text
1. DocumentUseCase.uploadDocument() 트랜잭션 시작
2. DocumentService.uploadDocument()에서 파일 저장과 document row 저장
3. 아직 바깥 UseCase 트랜잭션이 끝나지 않아 DB commit 전 상태
4. 같은 UseCase 안에서 @Async 문제 생성 호출
5. 비동기 스레드가 documentId로 DB 조회
6. 커밋 전 데이터라 조회 실패
7. DOCUMENT_NOT_FOUND 발생
```

### 변경 시나리오

```text
1. DocumentUseCase.uploadDocument() 트랜잭션 시작
2. DocumentService.uploadDocument()에서 파일 저장과 document row 저장
3. DocumentUploadedEvent 발행
4. DocumentUseCase.uploadDocument() 종료와 함께 DB commit
5. @TransactionalEventListener(AFTER_COMMIT)가 커밋 이후 이벤트 수신
6. 이벤트 핸들러가 @Async 문제 생성 호출
7. 비동기 스레드가 이미 커밋된 document row 조회
8. 문제 생성 진행
```

### 처리 내용

- 문서 업로드 완료를 나타내는 `DocumentUploadedEvent`를 추가했다.
- `DocumentUploadedEventHandler`에서 `@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)`로 커밋 이후 기존 비동기 문제 생성을 시작하도록 변경했다.
- 사용자 활동 통계용 `DocumentRegisteredEvent`도 UseCase 트랜잭션 안에서 발행하고, 기존 모니터링 이벤트 핸들러의 `AFTER_COMMIT` 정책을 그대로 사용한다.

### 결정 이유

- `REQUIRES_NEW`로 내부 저장 트랜잭션을 강제로 분리할 수도 있지만, 바깥 UseCase 트랜잭션과 원자성이 어긋날 수 있다.
- `TransactionSynchronizationManager`를 직접 쓰는 방식도 가능하지만, 코드 이해 난도가 높아진다.
- 이 프로젝트에는 이미 모니터링 통계 적재에서 `@TransactionalEventListener(AFTER_COMMIT)` 패턴을 사용하고 있으므로 같은 방식으로 맞췄다.
