# TMK 개발 규칙

---

## API 버전 관리

- API 버전은 URL 경로에 명시한다.
- 자원 경로는 컨트롤러 상단 `@RequestMapping`에 둔다.
- 버전은 메서드 레벨 매핑에서 `ApiVersion` 상수로 관리한다.

예시:

```java
@RequestMapping("/admin/auth")
public class AdminAuthController {

    @PostMapping(ApiVersion.V1 + "/login")
    public ResponseEntity<ApiResponse<AdminLoginResponse>> login(...) {
        ...
    }
}
```

원칙:

- `"/v1"` 같은 문자열을 컨트롤러마다 직접 반복해서 쓰지 않는다.
- 하위 호환이 깨지는 변경이 생기기 전까지는 기존 버전을 유지한다.
- 새로운 버전이 필요하면 `ApiVersion.V2`를 추가하고, 구버전과 일정 기간 공존시킨다.

## Controller / ControllerDocs 규칙

- API Controller는 구현체로 둔다.
- Swagger 관련 어노테이션은 `ControllerDocs` 인터페이스에 둔다.
- Controller는 해당 `ControllerDocs` 인터페이스를 구현한다.

예시:

```java
public interface AdminAuthControllerDocs {

    @Operation(summary = "관리자 로그인")
    ResponseEntity<ApiResponse<AdminLoginResponse>> login(AdminLoginRequest request);
}
```

```java
@RestController
@RequestMapping("/admin/auth")
public class AdminAuthController implements AdminAuthControllerDocs {

    @Override
    @PostMapping(ApiVersion.V1 + "/login")
    public ResponseEntity<ApiResponse<AdminLoginResponse>> login(...) {
        ...
    }
}
```

## UseCase / Response 변환 규칙

- API UseCase는 가능하면 엔티티를 직접 반환하지 않고 `...Result` 형태의 반환 모델을 사용한다.
- Controller는 UseCase가 반환한 `...Response`를 그대로 응답한다.
- `Response`는 HTTP 응답 스펙 표현을 담당하고, `Result`는 UseCase의 반환 계약을 담당하도록 역할을 분리한다.
- Service는 비즈니스 로직을 수행하고 `...Result`를 반환한다.
- UseCase는 Service가 반환한 `...Result`를 `...Response.from(result)` 또는 `...Response.of(...)`로 변환한다.
- Controller 가독성을 해치지 않는 범위에서는 UseCase가 API의 `Request` DTO를 직접 받아도 된다.
- 조회 최적화를 위해 QueryDSL projection이나 별도 조회 모델을 사용하더라도, Service 앞단에서는 `Result -> Response` 구조를 우선한다.
- 단순 생성/조회/상태 변경 API라도 응답 DTO 생성 책임은 UseCase 또는 Response 정적 메서드에 두고, Service 내부에서 API Response DTO를 직접 만들지 않는다.
- `Result` 생성 책임도 Service의 private 변환 메서드에 두기보다 `...Result.from(entity)` 또는 `...Result.from(queryResult)` 같은 정적 메서드로 모은다.

예시:

```java
public record AdminAccountResult(
        Long adminId,
        String username,
        boolean active,
        OffsetDateTime createdAt
) {
}
```

```java
public record AdminAccountSummaryResponse(
        Long adminId,
        String username,
        boolean active,
        OffsetDateTime createdAt
) {
    public static AdminAccountSummaryResponse from(AdminAccountResult result) {
        return new AdminAccountSummaryResponse(
                result.adminId(),
                result.username(),
                result.active(),
                result.createdAt()
        );
    }
}
```

```java
AdminAccountResult result = adminAccountService.createAdminAccount(...);
return AdminAccountSummaryResponse.from(result);
```

## 트랜잭션 규칙

- 트랜잭션 경계는 기본적으로 UseCase에 둔다.
- Service도 자신의 작업 의도가 드러나도록 `@Transactional(readOnly = true)` 또는 `@Transactional`을 명시한다.
- Service의 트랜잭션 전파는 기본값인 `REQUIRED`를 사용해서 UseCase가 시작한 전체 트랜잭션에 참여하게 둔다.
- 클래스 레벨 기본값만 두고 끝내기보다, 조회 메서드는 `@Transactional(readOnly = true)`, 쓰기 메서드는 `@Transactional`을 메서드에도 가능하면 명시해서 읽기/쓰기 의도를 드러낸다.
- 조회 전용 UseCase는 `@Transactional(readOnly = true)`를 기본으로 사용한다.
- 생성, 수정, 삭제가 포함된 UseCase 메서드는 `@Transactional`로 쓰기 트랜잭션을 연다.
- 하나의 API 요청에서 Service 호출이 하나뿐이어도, 전체 비즈니스 작업의 트랜잭션 경계는 UseCase가 갖고 Service는 그 안에 참여하는 구조를 유지한다.
- Service에 `@Transactional`을 함께 두는 것은 별도 트랜잭션 분리를 의도하는 것이 아니라, 해당 작은 작업의 읽기/쓰기 성격을 명시하기 위한 것으로 본다.
- `readOnly` 여부는 DB 쓰기 기준으로 판단하고, Redis 같은 부가 작업이 있더라도 JPA 변경 감지/flush 정책을 함께 고려해 결정한다.

예시:

```java
@Component
@RequiredArgsConstructor
@Transactional(readOnly = true)
public class AdminAccountUseCase {

    @Transactional
    public AdminAccountSummaryResponse createAdminAccount(...) {
        ...
    }

    public List<AdminAccountSummaryResponse> getAdminAccounts() {
        ...
    }
}
```

```java
@Service
@RequiredArgsConstructor
@Transactional(readOnly = true)
public class AdminAccountService {

    @Transactional
    public AdminAccountResult createAdminAccount(...) {
        ...
    }

    public List<AdminAccountResult> getAdminAccounts() {
        ...
    }
}
```

## Stream 사용 규칙

- 메서드 호출 결과에 바로 `.stream()`을 이어 붙이지 않는다.
- 스트림 처리 대상은 먼저 지역 변수에 담은 뒤 `localVariable.stream()` 형태로 사용한다.
- 이 규칙은 스트림 시작점이 길어질수록 가독성이 떨어지는 것을 막기 위한 기준이다.

예시:

```java
List<AdminAccountResult> results = adminAccountService.getAdminAccounts();
return results.stream()
        .map(AdminAccountSummaryResponse::from)
        .toList();
```

피해야 하는 형태:

```java
return adminAccountService.getAdminAccounts().stream()
        .map(AdminAccountSummaryResponse::from)
        .toList();
```

## 정리 규칙

- 개발이나 수정 작업을 할 때, 변경 결과로 비어 있는 패키지 디렉터리가 생기면 함께 정리한다.
- 변경한 파일에 사용하지 않는 `import`가 남아 있으면 함께 제거한다.
- 정리 작업은 기능 변경과 분리하지 않고, 같은 작업 범위 안에서 같이 처리한다.

---

## 나중에 할 운영 작업

웹 클라이언트와 API 버전 전환을 안전하게 운영하는 작업은 가장 나중에 진행한다.

대상:

- 웹 클라이언트 버전 체크
- 구버전 프론트 강제 새로고침 유도
- `v1`, `v2` 공존 기간 운영 정책
- 구버전 API 제거 시점과 공지 정책

이 작업은 현재 구현 우선순위가 아니라, 핵심 API 개발이 끝난 뒤 운영 안정화 단계에서 진행한다.
